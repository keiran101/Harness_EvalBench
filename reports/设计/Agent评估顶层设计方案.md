# Agent 评估系统 · 顶层设计方案

> **指导来源**：《AI Agents in Depth》（中文版）第六章「Agent 的评估」
> **定位**：独立于任何具体实现的顶层设计，作为后续框架实现的蓝图
> **核心问题**（第六章开篇原话）：*怎么判断 Agent 变好了还是变差了？*

---

## 0. 设计定位与总纲

评估不是 Agent 上线前的"验收环节"，而是贯穿 **设计 → 选型 → 迭代 → 后训练** 的主线方法论。

三条总纲，全部来自第六章：
1. **评估对象 = 模型 + Harness 组合体**，不是孤立的模型。同一模型在不同 Harness 下表现差异悬殊，必须能区分"模型能力不足"与"Harness 设计缺陷"。
2. **评估体系的首要价值不是给当前系统打分，而是让你快速、可靠地跟上模型演进**。新模型发布时，有体系的团队数小时出切换决策，没有的只能凭直觉。
3. **生产级评估是持续闭环，不是一次性考试**。从真实 bad case 中持续生成回归/边界任务，形成"环境 → 数据集 → 打分+归因 → 改进 → 更新评估集"的自演化循环。

---

## 1. 要解决的实际问题

设计这套评估系统，是为了回答以下具体、可操作的问题（对应第六章各节）：

| # | 实际问题 | 落到评估里的含义 |
|---|---|---|
| 1 | 现在的系统到底行不行？ | 区分**能力上限**与**业务可靠性**，不能只看头条分数 |
| 2 | 改了一处（prompt / 工具 / 模型 / 记忆）是变好还是变坏？ | 消融实验 + 端到端回归，防止"捡芝麻丢西瓜" |
| 3 | 瓶颈在模型还是 Harness？ | 模型替换实验（model swap）vs 消融实验，两种不同定位手段 |
| 4 | 哪些失败是系统性的，值得修？ | 失败归因：标出主要错误类别与**首个不可接受行为的步骤** |
| 5 | 新模型发布，要不要切？ | 在自己的评估集上完整测试，统计显著性判断回归，数据驱动决策 |
| 6 | 分数为什么不可信（污染 / 饱和 / 捷径）？ | 评估集防泄漏、任务分布系统性、验证器健壮性 |
| 7 | 生产环境是不是在退化？ | 在线采样评估 + 可观测性（trace 挂分）+ 漂移检测 |
| 8 | 失败怎么变成训练/迭代信号？ | bad case → 回归测试集；评估环境与后训练环境同源 |

## 2. 设计重点（优先级）

按第六章的权重，不可妥协的重点排序：

1. **评估对象先定对**：模型 + Harness 组合体。否则一切分数都无法指导改进。
2. **先定义"成功"再谈工具和数据**：正文先建指标体系（什么算成功），再展开环境/数据集。避免"先讨论工具、最后才定义成功"。
3. **拆开两层指标**：`Pass@k`（能力上限）与 `Pass^k`（业务可靠性）回答完全不同的问题，必须分别报告。
4. **失败可审计归因**：不只看最终通过与否，要对每条失败轨迹定位首个错误步。
5. **数据集是地基中的地基**："测什么"决定评估有没有意义。指标再科学、judge 再强，数据集有污染/偏甜蜜点/不可验证，结论全是假的。
6. **持续闭环而非一次性考试**：从 bad case 持续生成回归与边界任务。
7. **统计显著性 + 防泄漏**：分数差异要确认超出噪声带宽；评估集题目与训练数据严格隔离（红线）。

## 3. 范式转向：不是 QA，是 Task

这是整个设计必须首先确立的范式，否则后面的指标、环境、数据集都会走偏。

### 3.1 QA 与 Task 的本质区别

| 维度 | QA（传统 LLM 评估） | Task（Agent 评估） |
|---|---|---|
| 交互形态 | 单轮问答 | 多步、多工具、有状态、长程 |
| 评估单元 | 一个样本（prompt→response） | 一条**轨迹 / episode**（动作序列 + 观察 + 状态变迁） |
| 验证对象 | 最终答案文本（字符串匹配 / 语义判分） | **环境最终状态**（DB 状态、文件系统、URL、应用状态） |
| 成功标准 | "答对题" | "在约束下达成目标状态" |
| 过程重要性 | 基本忽略 | 核心：中间任一步错都会级联崩溃 |
| 指标外延 | 准确率 / F1 | 准确率 + 路径效率 + 工具选择 + 澄清质量 + 危险动作前确认 |

### 3.2 为什么必须是 Task
- Agent 的定义是"在环境中通过一系列有状态动作达成目标的系统"。**这条轨迹（Trajectory）才是评估单元**，不是最终那句话。
- 失败会在多步、多工具调用中**复利式放大**：一次小概率失误 → 级联错误。所以必须能定位**首个错误步**。
- 验证必须检查**环境状态**而非文本："表面完成但实质错误"的情况（点击了提交按钮但字段填错被服务端拒绝）只有查 DB/文件系统才能发现。
- 成功标准要拆成两层：**达成目标**（目的）与**过程合规**（是否越权、是否危险动作前确认、是否澄清）。

> 这一转向直接决定了后面的架构：评估环境必须能暴露并程序化验证状态（工具调用型），或在真实策略约束下模拟用户（人机交互型）；指标体系必须包含过程维度。

## 4. 完整整体的设计（系统架构与闭环）

### 4.1 三层结构（来自本章导读）

```
第一层  评估设计  →  指标体系（什么算成功）
                    评估环境（在哪里测）
                    数据集  （测什么）
        ↓
第二层  评估方法  →  LLM-as-a-Judge · 配对比较与模型排名 · 确定性验证器
        ↓
第三层  评估驱动决策 → 模型选型 · 架构优化（Harness） · 持续迭代
```

### 4.2 端到端闭环（来自 6.12 本章小结）

```
评估环境(自动化测试基础设施)
   → 评估数据集(端到端任务 + trajectory prefix 边界)
   → 自动化评估方法(确定性验证器 + LLM-Judge + Rubric) 打分并生成失败归因
   → Benchmark / bad case 分析揭示改进方向
   → 系统改进修复问题
   → 更新评估环境与数据集  → （新一轮迭代）
```

### 4.3 离线 / 在线双轨（生产级）

- **离线仿真**：能否发布（环境可 reset、高吞吐、带验证器）。
- **在线采样**：是否退化（对生产流量跑 evaluator、设阈值告警、捕获 prompt/task/data drift）。
- **可观测性**：分布式 tracing（OTel 语义约定），把 evaluator 分数挂到 span / session，让差结果定位到具体节点；session 级与 node 级指标并重。
- **A/B 测试**：一次只改一个变量（prompt / 工具 / 模型 / 记忆策略），分层证据（离线仿真 → 受限灰度 → 质量门禁）做决策。
- **数据策展闭环**：失败样本 / 低分会话 → 回归 / 压力 / 合规测试集，测试集随 Agent 一起演化。

### 4.4 组件清单

| 组件 | 职责 |
|---|---|
| Dataset Registry | 数据集版本化、参数化模板、复杂度标签、防泄漏标记 |
| Environment | 工具调用型 / 人机交互型 / 仿真环境，提供状态与验证器 |
| Agent Under Test + Harness | 被测对象（模型 + 工程） |
| Verifier | 确定性验证器（状态检查、FAIL_TO_PASS / PASS_TO_PASS 双检） |
| Judge | LLM-as-a-Judge（Rubric + 锚定 + 偏差校正），可插拔 |
| Metrics Engine | Pass@k / Pass^k / 过程指标 / 统计显著性 |
| Report / Dashboard | 报告必须写清 k 口径、样本量、环境差异、未完成部分 |
| Regression Store | bad case → 回归/边界测试集的沉淀与回流 |

## 5. 评估指标体系设计

### 5.1 两层核心指标（不可合并）
- **能力上限**：`Pass@k`（k 次独立采样至少 1 次成功）、`Best@k`。回答"最好一次能不能成"。
- **业务可靠性**：`Pass^k` / `Pass consecutive@k`（连续 k 次稳定通过）。回答"每次都别出错"。
- **k 的口径必须写清**：是同一任务的 k 次独立采样，还是生产流水线上连续 k 个任务。两者语义不同。
- 选型时：**关键操作场景优先 `Pass^k`**（盯稳定性）；**探索性任务优先 `Pass@k`**（盯上限）。

### 5.2 过程指标（白盒，从黑盒到看每一步）
步效用、规划质量、工具选择正确率、路径收敛度、路径效率（步数 / 冗余动作）、澄清质量、危险动作前确认。

### 5.3 安全 / 鲁棒性指标
权限绕过率、注入成功率、轨迹覆盖率。

### 5.4 报告纪律
评估报告必须写清：k 次尝试的口径、样本量、环境差异、尚未完成的部分。避免"分数好看但不可复现"。

### 5.5 复杂度分层对应改进方向
以 GAIA 三级为例：L1 失败 → 基础工具使用问题；L2 失败 → 多步规划/信息整合；L3 失败 → 长序列思考/分层架构/后训练。不同层指向不同改进手段。

## 6. 评估环境设计

### 6.1 两类核心范式
- **工具调用型**：环境暴露一组工具（API / DB / 文件系统），用**程序化验证器**检查最终状态或输出（SWE-bench 跑单测、WebArena 检查 URL/DB 状态）。可自动化、可回归、高吞吐。
- **人机交互型**：由 LLM 或脚本扮演用户，多轮对话 + 真实工具调用，验证在真实策略约束下完成任务（τ-bench）。关键设计是**渐进式信息透露（Progressive Disclosure）**——不一次性给全信息，按 Agent 提问逐步透露；以及**双控环境（Dual-Control）**——用户模拟器实际改变环境状态，Agent 必须观察到变化才能继续。

### 6.2 仿真环境（连接后训练）
- 把评估环境升级为可 reset、高吞吐、带验证器的仿真器，成为**后训练的桥梁**（评估指标即训练目标 / 可验证奖励 RLVR）。
- 难点是 **sim-to-real 差距**，手段是**领域随机化**（物理参数、视觉外观、传感器噪声大范围随机）。
- 每个 episode 必须能把环境重置到**确定、干净的初始状态**。

### 6.3 环境设计要点
可复现、可控、真实性、可 reset、带即时反馈、防死记（随机化）。

## 7. 数据集设计（深入）

> 这是地基中的地基。下面按第六章 6.4 的六个小节展开，逐条给出设计规则。

### 7.1 六大核心挑战与设计对策

| 挑战 | 设计对策（PDF 实例） |
|---|---|
| **明确性 vs 开放性** | 任务目标明确但路径开放。GAIA：目标明确（找某宇航员太空时长），如何搜索/验证由 Agent 自主决定 |
| **真实性 vs 可控性** | SWE-bench Verified 从 2294 题人工筛至 500 题（淘汰率 71%），保真实又提可控 |
| **多样性 vs 系统性** | AndroidWorld 116 任务横跨 20 应用，标注核心能力维度；参数化生成无限变体 |
| **成本 vs 覆盖** | GAIA 精选 466 题分三级；Verified 靠提信噪比把成本降约 80% |
| **数据泄漏防范** | canary GUID、时间新鲜度、参数化随机实例、答案稀有性 |
| **质量迭代** | 高淘汰率人工筛选 + 标准化标注指南 + 暴露问题系统修复（OSWorld-Verified） |

### 7.2 任务描述精确性设计
- 明确信息源约束、时间范围、主题、查询目标，确保答案唯一（GAIA Level 3 精确到格式）。
- **已知信息 / 任务指令分离**（τ²-bench）：已知信息 = 用户当前掌握事实；任务指令 = 模拟器如何渐进透露信息，含 **事实锚定要求（Grounding）**——必须基于工具真实返回回答，不能编造。
- 每个元素尽量可机械化验证（Terminal-Bench：文件路径、权限数值、证书参数、日期格式）。

### 7.3 复杂度层次化设计
- 诊断价值是核心：不同层失败指向不同改进方向。
- GAIA 三级：L1（1–2 工具）→ L2（多步思考）→ L3（复杂组合）。
- τ²-bench 业务复杂度：信息查询 → 多步流程 → 故障诊断 → 策略判断。
- Terminal-Bench 技术 × 操作复杂度双维分层。

### 7.4 可验证性与客观性保障
- 确定性验证器优先：SWE-bench 的 **FAIL_TO_PASS**（修复前失败、修复后通过，证明问题被解决）+ **PASS_TO_PASS**（修复前后都通过，证明没引入新 bug）双验证。
- 二元奖励 + 多层检查（τ²-bench：DB 状态 + 对话关键词 + 流程合规性，全过才算成功）。
- 验证基于**最终状态**而非操作序列（AndroidWorld 验证 UI 最终状态），防止"表面完成"。
- 严格格式 → 精确字符串匹配，确保客观可复现。

#### 7.4.1 工具面策略（决策记录 2026-08-23）
**工具是 harness 的一部分。** 判定成功/失败只依据：① 最终环境状态（落盘文件内容/存在性/目录集合，或内存 dict 键值）；② 过程硬约束（confirm/clarify/error_recovery 类模板对轨迹动作前缀的检查，如 `confirmed_before` / `irreversible_without_confirm`）。**verifier 不校验轨迹调用的工具是否属于数据集声明的 `available_tools`。**

- **默认不限定工具（满血评估）**：被测 agent 使用其完整工具面（含 harness 自带、数据集未声明的工具）完成任务，是**允许且被计入其真实能力**的。横向对比时，工具面差异属于被测 harness 的能力差异，如实反映在分数中——"完整 harness 包括 tool 才是真正评估 harness 满血性能"。
- **限定工具仅是可选模式（暂不实现）**：若将来需要"限定公平条件下评估其余 harness 组件"（同一工具面下只比决策/编排/状态管理），可把 `available_tools` 升级为 verifier 第四通道（轨迹越界工具 → 判 Fail）。该分支当前**不实现**，`available_tools` 保留为声明性字段（数据集可读性/未来扩展）。
- **实现注意**：被测 agent 若因环境限制（如本地 LLM 端点 n_ctx 过小）必须裁剪工具面才能运行，属**技术妥协而非语义限定**，须在对应报告的 `_meta`/说明中注明"工具面已裁剪"，避免与满血评估数字误比。

### 7.5 任务分布系统性设计
- 四维覆盖：能力维度 × 难度维度 × 场景维度 × 边界情况。
- **陷阱任务**（τ²-bench）：用户谎称"客服已批准取消"但不符合政策，测压力/误导下的策略判断。
- 跨技术栈组合任务（Terminal-Bench）测系统思维。

### 7.6 数据质量控制与迭代
- 高淘汰率是对质量的必要投资（SWE-bench Verified 500/2294）。
- 标准化标注指南，为每项检查定义具体标准与示例，保证标注者一致性。
- 暴露问题系统修复：OSWorld-Verified 15 个月暴露 300+ 问题（环境/描述/逻辑/初始状态四类），10 人小组两个月系统修复，并行加速 50×，轨迹数据公开形成社区审查良性循环。

### 7.7 防泄漏专项设计（红线）
- **canary GUID**（Terminal-Bench）：模型若输出该 GUID 即证明泄漏。
- **时间新鲜度**（SWE-bench-Live）：持续收录模型训练截止日之后新 issue。
- **参数化模板随机实例**（τ²-bench / AndroidWorld）：用户姓名、订单号、日期等每次随机生成。
- **答案稀有性**（GAIA）：高度具体事实难从训练数据原样出现。
- **红线**：可复用环境的构造机制，但评估集的具体题目必须与训练数据严格隔离。

### 7.8 参数化模板机制（可复用资产）
一个任务不是静态文本，而是可动态实例化的模板（如"将联系人 [NAME] 电话改为 [NEW_PHONE]"），每次随机生成参数。好处：
1. **防记忆**：参数每次不同，无法回放固定序列；
2. **增多样**：一个模板生成无限实例；
3. **支持对比实验**：固定部分参数、只变其他，精确测量单因素影响。

### 7.9 数据集 → 回归/边界测试闭环
- 从真实 bad case 持续生成回归任务。
- **trajectory prefix 边界集**：固定前 N 步，检查作用域判断、当前指令覆盖、澄清、危险动作前确认（用户记忆只是其一案例）。
- 端到端回归保证基本任务不退化，prefix 边界集直接查过程合规。

## 8. LLM-as-a-Judge 设计

### 8.1 何时用 / 何时不用
- **用**：开放式任务（客服对话、报告撰写、多模态生成）无标准答案时。
- **不用**：输出有严格格式（JSON / 邮编 / 可执行断言）时，确定性代码校验更准更省。

### 8.2 Rubric 工程化
- **结构化维度 + 加权**：事实准确性 / 任务完成 / 推理质量 / 工具效率 / 表达清晰度，各自独立打分再加权，避免把不同维度混为一谈。
- **基于专家指导**：Rubric 必须反映领域知识、捕捉核心事实与推理步骤（如医疗问答需含诊断标准与必须避免的错误），缺乏专业基础的 Rubric 只能抓语言流畅度等表面特征。
- **硬性否决项**：触发即否决（防关键词堆砌式奖励作弊、防回避棘手问题）。

### 8.3 锚定评分（Anchor Scoring）
每个分数档给明确行为锚点（如 1/4/7/10），提供具体示例与边界案例帮助区分模糊情况，防止分数向中间压缩、区分度下降。

### 8.4 偏差分类与校正
- **位置偏差**：pairwise 中偏好靠前选项 → 每轮随机化顺序，关键项跑两种顺序取平均。
- **长度偏差**：长回答被高估 → 显式指令"长度不是质量信号"。
- **自我增强 / 风格偏差**：judge 偏好某种措辞 → 多模型集成（ensemble）缓解。

### 8.5 可审计与迭代
- Rubric 是迭代产物：通过试用收集评价者分歧、逐步完善，从抽象准则落到可执行档位。
- **失败归因作为 Judge 输出的一部分**：标出主要错误类别、首次出现不可接受行为的步骤，直接喂给改进闭环。

### 8.6 可靠性保障
- 周期性用人工标注校准 judge。
- 多评委 / 集成提升稳健性。
- 配对比较用 Bradley-Terry 类模型做模型排名时，注意人类偏好可能非传递，需在敏感场景人工复核。

## 9. 落地路线图（简述）

1. **先立指标体系与 k 口径**（§5），定义清楚"成功"。
2. **搭最小评估环境**（§6）：先工具调用型 + 确定性验证器跑通。
3. **建数据集**（§7）：参数化模板 + 防泄漏 + 复杂度标签 + 验证器双检。
4. **接 LLM-Judge**（§8）：Rubric + 锚定 + 偏差校正，先做失败归因输出。
5. **补可观测性与在线采样**（§4.3），形成离线/在线双轨。
6. **闭环化**：bad case → 回归测试集，测试集随 Agent 演化。

> 本方案是蓝图，不绑定任何既有实现。其模块边界（指标 / 环境 / 数据集 / Judge / 归因 / 报告）可直接映射为后续框架的代码包。
