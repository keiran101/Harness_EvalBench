# DeepSeek 错误样本：与数据集、与工具有关吗？

> 分析对象：`results/eval_deepseek_retrieval_keycases_20260825_203404.json`（33 模板 × k=2 = 66 轨迹，pass_k=0.652）
> 核心问题：**deepseek 的失败，到底和「数据集特征」有关，还是和「它实际使用的工具」有关？**

## 一句话结论

**两者都有关，而且是「数据集触发 → 工具选择落错」的链式关系。**

- **直接机制（工具）**：失败几乎 100% 发生在「没调用 `read` 工具」时——deepseek 用了 `glob` 列目录就直接作答（捷径行为）。这是**工具选择失败**，不是读不懂。
- **上游触发（数据集）**：任务越复杂（gold 文件越多、干扰项越强、tier 越难），deepseek 越容易触发这个「不读」捷径。无干扰任务失败 12.5%，有干扰任务失败 42%（3.4 倍）。
- 串联：**数据集复杂度 → 触发 deepseek 跳过读取 → 读不到 gold → 失败**。工具选择是中介机制，数据集特征是触发条件。

---

## 分析方法与数据校正

1. **通过标签重建**：轨迹级无 `passed` 字段，且 `pass_k=0.5` 模板需区分两条 seed。用「gold 真值覆盖率」重建标签（`coverage≥1.0 → PASS`，否则 `FAIL`），并强制与模板 `pass_k` 一致（pass_k=1.0 全过 / 0.0 全挂 / 0.5 按覆盖率分）。最终 PASS=43 / FAIL=23，43/66=**0.652 与 overall pass_k 完全吻合**，标签可靠。
2. **路径归一化校正**（修正上轮误判）：动作字符串里路径是双反斜杠 `v3\\deploy.md`，原 `norm` 把 `\\` 换成 `//` 导致与 gold 匹配失败。已改为「反斜杠→斜杠 + 折叠多斜杠」，覆盖率计算才正确。
3. **难度代理**：除数据集自带的 `gold_docs` 数外，从 `state_before`（环境文件 dict）提取 `env_n`（搜索空间大小）与 `distr_env`（环境内被标注为"草稿/忽略/无关"的干扰文件数）。

## A. 与「使用的工具」的关系（直接机制）

| 指标 | PASS (n=43) | FAIL (n=23) |
|---|---|---|
| 使用 `read` 工具的比例 | **1.000** | 0.391 |
| 仅 `glob` 列目录即作答（glob-only）比例 | **0.000** | **0.609** |
| 平均 read 次数 | 4.14 | 1.48 |
| 平均 discovery(glob/ls) 次数 | 1.63 | 1.30 |
| 使用的工具种类数 | 2.14 | 1.43 |

**决定性证据**：
- **`0-read → FAIL` 精确率 = 1.000**：14 条完全没读文件的轨迹**全部失败**，无一幸免。
- **用了 read → PASS 率 = 0.827**：只要它读了，82.7% 都能过。
- PASS 轨迹 **100% 用了 read**，FAIL 轨迹 61% 是「glob 一下就答」。

**含义**：deepseek 的"读能力"其实不差（读了就 83% 过），真正的问题是**工具选择**——它倾向于用 `glob` 列目录代替真正 `read` 内容，是一条"捷径行为"而非能力瓶颈。

## B. 与「数据集」的关系（触发/放大因素）

### B1. 数据集特征在 PASS vs FAIL 的差异

| 数据集特征 | PASS | FAIL |
|---|---|---|
| 平均 gold 文件数 (gold_n) | 2.49 | **3.00** |
| 平均环境文件数 (env_n，搜索空间) | 3.84 | **4.74** |
| 平均环境干扰文件数 (distr_env) | 0.86 | **1.26** |

### B2. 失败率随具体特征的梯度

| 维度 | 分组 | 失败率 | 对比 |
|---|---|---|---|
| **gold 文件数** | 1–2 个 | 0.250 | — |
| | 3–4 个 | **0.441** | 1.8× |
| **tier 难度** | base | 0.150 | read-skip 0% |
| | middle | 0.409 | read-skip 18% |
| | hard | **0.458** | read-skip **42%** |
| **环境干扰文件** | 0 个 | **0.125** | — |
| | 1–2 个 | **0.420** | 3.4× |
| **指令含干扰词** | 有 | 0.396 | 1.8× |
| | 无 | 0.222 | — |
| **数据集来源** | keycases（陷阱题） | **0.667** | read-skip 50% |
| | 普通 retrieval | 0.317 | read-skip 18% |

**关键观察**：
- 失败率随 **gold 数、环境文件数、干扰数、tier** 单调上升。
- **干扰是强信号**：环境有干扰文件时失败率 3.4 倍；而无干扰时 read-skip 率=0%、失败率仅 12.5%。
- **keycases 是"答案泄漏/干扰"陷阱题**，deepseek 在这里失败 67%、跳过读取 50%，是普通 retrieval 的 **2.7 倍**——说明这类"答案就在指令里、不必真读"的题，恰恰最容易诱使它不读。

## C. 二者如何串联（核心结论）

错误不是单一因素，而是**上游触发 + 中介机制**的链路：

```
数据集复杂度（gold 多 / 干扰强 / tier 难）
        │  放大效应
        ▼
deepseek 触发 "glob 列目录即作答" 捷径（工具选择失败）
        │  中介机制
        ▼
未调用 read → 读不到 gold（coverage↓）
        │
        ▼
FAIL（0-read → 100% 失败）
```

- **工具选择是错的"落点"**：即便任务简单，只要它选了 glob-only 就必挂；
- **数据集是错的"扳机"**：任务越复杂/干扰越多，它越容易扣下这个扳机（hard 层 read-skip 42%、keycases 50%，而 base 0%、无干扰 0%）。

> 因此，单独说"和工具有关"或"和数据集有关"都不完整——**数据集决定概率，工具选择决定结果**。这与 pi/opencode 的失败模式同源（三家都暴露"跳过读取"），但 deepseek 的触发阈值最低、最关键 cases 最易翻车。

## D. 典型轨迹样例（佐证）

**样例 1 — 纯跳过读取（glob-only 捷径）**
- `hard_retrieval_002` seed0：仅 `glob:{"pattern":"**/*"}` → 直接作答，0 次 read → FAIL
- `keycases_hard_002` seed0：`glob pay_api.md` / `glob pay_callback.md` / `glob pay_refund.md` 三次列目录 → 直接作答 → FAIL（答案泄漏陷阱，它真没读）
- `middle_retrieval_005` seed0：仅 `glob:{"path":"deploy/","pattern":"**/*.yaml"}` → FAIL

**样例 2 — 读了但内容被管道折叠（read-but-mangled，少数型）**
- `base_retrieval_007` seed0：`glob *.log` → `pwsh Get-Content a.log,b.log,c.log,d.log | Select-Object -Last 1` → 管道只取最后一行，gold 内容被丢弃 → FAIL（覆盖率<1，但确实调用了 read 类工具）

---

## 修复建议（双管齐下，性价比排序）

1. **堵「不读」捷径（针对工具机制，收益最大）**：在 deepseek 系统提示显式强制"先 `read` 再作答"，或对"未 read 即答"在 verifier 加惩罚。预计可把 pass_k 从 0.65 拉到 0.85+（堵住 61% 的 glob-only 失败）。
2. **强化干扰/陷阱题处理（针对数据集触发）**：对 keycases、高 distr_env 任务加 few-shot，示范"即使答案看似已知也要读 gold 文件核实"。
3. **降低 flaky**：deepseek 在 hard 层 seed_sensitivity=0.208（9/33 模板随种子波动），调低 temperature 可提升稳定性。
