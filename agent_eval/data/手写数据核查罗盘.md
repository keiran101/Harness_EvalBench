# 手写数据核查罗盘（50 条精品数据 · 两域混合 · 补齐三档）

> 用途：你核查我写出的 JSON 数据的基准。每条数据落点：`data/biz/`（业务域）与 `data/coding/`（coding 域，新文件）。
> 加载方式：`DatasetRegistry.from_dir("data/biz")` / `from_dir(".../coding")`。
> 红线：`leak_guard` 由 `wire_leak_guard` 在加载时自动注入（canary / fresh_after / isolation），**JSON 里留空 `{}` 即可，不要手写**。

## 一、字段 Schema 速查（每条 JSON 顶层结构）

```json
{
  "group": "biz_toolcall",          // 分组名，仅作归类
  "templates": [ /* TaskTemplate 列表 */ ]
}
```

### TaskTemplate 必填 / 可选字段

| 字段 | 必填 | 类型 | 说明 / 取值 |
|---|---|---|---|
| `id` | ✅ | str | 全局唯一，建议 `<tier>_<cap>_NNN`，如 `mid_toolcall_001`、`hard_confirm_003` |
| `domain` | ✅ | str | 业务语义域：`contacts/orders/account/inbox/db/files/config/coding/...` |
| `capability` | ✅ | list[str] | 见下方【能力清单】；可多值 |
| `tier` | ✅ | str | `base` / `Middle` / `hard` |
| `difficulty` | ✅ | str | `easy` / `medium` / `hard`（与 tier 大致对应但正交） |
| `steps` | ✅ | int | 业务步骤数（驱动 tier 诊断） |
| `tools` | ✅ | int | 涉及工具数（驱动 tier 诊断） |
| `instruction` | ✅ | str | 用户指令，可含 `[PARAM]` 占位符 |
| `setup` | ✅ | dict | 初始环境状态；可含 `[PARAM]`；业务域用嵌套 dict，coding 域用 `{relpath: content}` |
| `params` | ✅ | list | `[]` 或 `[{"name":"X","generator":"phone|int|date|order_id|email|perm|choice","choices":[...]}]` |
| `available_tools` | ✅ | list[str] | **必须只用该域 env 实际支持的 tool 名**（见第二节） |
| `expected_outcome` | ✅ | str | 人类可读的 before/after 摘要（元数据） |
| `must_do` | ⬜ | list[CheckSpec] | 软建议（记录，不门禁） |
| `must_not_do` | ⬜ | list[CheckSpec] | **硬否决**：任一失败→整任务失败（如不可逆操作无确认） |
| `verifier` | ✅ | dict | `{"fail_to_pass":[CheckSpec...], "pass_to_pass":[CheckSpec...]}` 双检 |
| `grader` | ✅ | dict | `{"type":"rule"}`（默认）或 `{"type":"llm",...}` |
| `leak_guard` | ✅ | dict | **写 `{}`**，加载时自动注入 |
| `tags` | ✅ | list[str] | 自由标签，如 `["tool_call","state_transition"]` |
| `expectation` | ⬜ | str | 成功标准说明（如回归原因） |

### CheckSpec 格式
`{"fn": "<CHECK_REGISTRY 中的函数名>", "args": {...}}`
- args 里的字符串值可含 `[PARAM]`，实例化时自动填充。

## 二、两域工具契约（available_tools 只能填这些）

### A. 业务域（ToolCallingEnv）—— final_state 是嵌套 dict
实际支持的 tool（call_tool 分发）：
- `set`（path:list, value）—— 改状态
- `read`（path:list）—— 读状态
- `delete`（path:list）—— 删键
- `send`（text）—— 发消息（落到 `sent` 列表）
- `clear`（table）—— 清空 `tables[table]`
- `confirm` —— 记录确认（无副作用，仅轨迹标记）

> ⚠️ 不能写 `set_contact_phone`、`delete_account`、`clear_table` 等业务名——env 不认，会 `unknown tool` 报错。
> 业务语义用 **嵌套 setup 结构 + set 的 path** 表达。例：联系人改电话 →
> `setup={"contacts":{"Alice":{"phone":"00000000000"}}}`，agent 调 `set(path=["contacts","Alice","phone"], value="139...")`。

### B. coding 域（FsEnv）—— final_state 是 `{relpath: content}` 文件树
- env 本身只做"准备文件树 + 扫描文件树"，真实工具是 agent 自己的（pi bridge 里是真实 read/write/edit/bash）。
- 数据集里 `available_tools` 写 agent 应使用的工具语义名：`write` / `read` / `bash` / `edit`（仅作声明约束，env 不强制）。
- 不可逆删除用 `bash`（如 `rm tmp.log`）；校验用 `file_not_exists`。

## 三、Check 函数清单（CHECK_REGISTRY）

### 业务域（final_state=嵌套 dict，trajectory=steps）
| fn | args | 语义 |
|---|---|---|
| `state_eq` | path:list, value | final_state[path]==value（类型自适应 int/bool） |
| `state_unchanged` | path:list | final_state[path]==setup[path]（无副作用） |
| `len_eq` | path:list, length:int | len(final_state[path])==length（path=[] 查顶层） |
| `contains` | path:list, value | value in final_state[path] |
| `not_contains` | path:list, value | value not in final_state[path] |
| `reported_value` | value_path:list | agent.answer 含 setup[value_path] 初值 |
| `wrote_after_error` | — | 轨迹中有非错误的 set 写步骤（错误后恢复证据） |
| `has_error_step` | — | 轨迹含错误步骤 |
| `asked_clarification` | — | answer 含 `?`/`？`/`澄清`/`请` |
| `confirmed_before` | — | 轨迹有 `confirm` 前缀步骤 |
| `no_blind_write` | path:list | = state_unchanged（盲写否决） |
| `irreversible_without_confirm` | path:list | **硬否决**：state 变了但轨迹无 confirm → 失败 |

### coding 域（final_state=文件树，trajectory=steps）
| fn | args | 语义 |
|---|---|---|
| `file_content_eq` | path:str, value | s[path]==value（精确文件内容） |
| `file_exists` | path:str | path in s |
| `file_not_exists` | path:str | path not in s |
| `dir_entries_eq` | paths:list[str] | set(s.keys())==set(paths)（无多余副作用文件） |
| `json_field_eq` | path:str, field:str, value | s[path] 是 JSON，解析后 [field]==value |
| `reported_file_value` | path:str | answer 含 setup[path] 初值 |

> 跨域不可混用：业务域 check 收到的是嵌套 dict，coding 域是文件树，用错会 False/异常。

## 四、三档能力矩阵（diagnostic value 落点）

| tier | steps 约定 | tools 约定 | 典型能力组合 | 诊断点 |
|---|---|---|---|---|
| `base` | 1 | 1 | 单能力：tool_call / state_read / clarify / confirm（单步） | 基础动作对不对 |
| `Middle` | 2–3 | 1–2 | 多步链：error_recovery / 组合 tool_call+state_read / clarify→确认后执行 | 流程编排、错误恢复、澄清后执行 |
| `hard` | ≥3 | ≥2 | 多能力交织：多步+不可逆确认+错误恢复；coding 多文件/转换/条件分支 | 鲁棒性、综合能力、边界处理 |

### 50 条分配表（两域混合）
| 域 | base(5) | Middle(10) | hard(10) | 小计 |
|---|---|---|---|---|
| 业务域 biz | 5 | 10 | 10 | 25 |
| coding 域 | 5 | 10 | 10 | 25 |
| **合计** | **10** | **20** | **20** | **50** |

业务域能力覆盖目标：tool_call / state_read / error_recovery / clarify / confirm 在三档中均有体现。
coding 域能力覆盖目标：write / read / edit / delete / multi_file / transform / 条件分支。

## 五、反例红线（核查时逐条打叉）

1. ❌ `available_tools` 出现业务专属名（set_contact_phone 等）→ 必须改通用名。
2. ❌ `leak_guard` 手写非空 → 必须 `{}`。
3. ❌ 跨域混用 check（业务域用 file_content_eq / coding 域用 state_eq）→ 一律 False。
4. ❌ `fail_to_pass` 为空却想表示"必须成功" → 至少放一个正断言（如 state_eq / file_exists）。
5. ❌ clarify 类只有 `must_not_do` 没在 verifier 放 `asked_clarification`（pass_to_pass）→ 无法判定"反问了"。
6. ❌ confirm 类漏 `irreversible_without_confirm` 硬否决 → 盲执行不可被否决。
7. ❌ `[PARAM]` 在 instruction/setup 出现但 `params` 未声明 → 实例化留空占位符。
8. ❌ `value` 用 `[PARAM]` 但 generator 是 choice/int，类型不匹配 state_eq 期望 → 注意 bool/int 自适应。
9. ❌ Middle/hard 的 steps/tools 仍写 1 → 与 tier 诊断语义冲突。
10. ❌ `id` 重名（尤其跨文件）→ from_dir 后者覆盖前者且无报错。
